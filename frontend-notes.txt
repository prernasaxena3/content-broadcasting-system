CONTENT BROADCASTING SYSTEM — FRONTEND NOTES
============================================================


1. PROJECT STRUCTURE
--------------------

The project is organized around Next.js 14's App Router and splits concerns by domain rather than by file type. Here is how each folder is used and why.

app/
    The App Router entry point. Route groups are used to separate concerns without affecting URL paths. The (auth) group wraps the login page with its own minimal layout. The (dashboard) group wraps all protected pages for teachers and principals with the shared dashboard layout, including the navbar and auth guard. The live/[teacherId] folder is a public dynamic route — it requires no authentication and is intentionally kept outside both route groups so it inherits no protected layout. URLs are unaffected by the route group parentheses.

components/
    Split by domain into auth/, dashboard/, content/, principal/, live/, and shared/ subfolders. This keeps each domain's components self-contained. The shared/ folder holds components that are used across multiple roles — StatusBadge, EmptyState, ErrorState, SkeletonLoader, and Navbar. The ui/ folder is auto-generated by shadcn and holds the base primitives. Components in domain folders are never imported into unrelated domains; they go through shared/ if reuse is needed.

services/
    All API calls are centralized here. No component imports axios or calls fetch directly. There are three service files: auth.service.js, content.service.js, and approval.service.js. Each function in these files currently returns mock data but is structured identically to a real API call. The actual API call is written as a comment directly above or below the mock return. To connect a real backend, only the return statement inside each function needs to change — everything else in the component, hook, and Redux layers stays untouched. services/api.js holds the shared Axios instance.

store/
    Redux Toolkit store with three slices: authSlice, contentSlice, and approvalSlice. Each slice owns one domain of state and exports its own actions and selectors. The store is configured in store/index.js.

hooks/
    Custom hooks — useAuth, useContent, and useApprovals — abstract all Redux dispatch and selector logic away from components. Components only call functions returned by these hooks. This keeps component files clean and makes the Redux wiring easy to change in one place.

mock/
    Contains mock data for users and content. The service layer imports from here to simulate API responses during development. Mock data includes realistic field shapes (IDs, timestamps, statuses, subjects) so switching to a real API requires no structural changes in the components.

utils/
    Three utility files. constants.js exports role names, content statuses, subject options, and file size/type limits — all in one place so they are easy to update. validators.js contains Zod schemas for form validation. helpers.js contains pure functions for date formatting, deriving scheduling status from timestamps, and mapping statuses to display colors.

proxy.js
    Next.js middleware for server-side route protection. Runs on every incoming request before the page is rendered. Handles redirects based on token presence and user role.


2. AUTHENTICATION FLOW
-----------------------

Step 1: The user submits the login form with an email and password.

Step 2: LoginForm.jsx calls loginUser() from auth.service.js, passing the credentials.

Step 3: The service validates the credentials against the mock users array. If valid, it returns a user object and a token string. If invalid, it throws an error.

Step 4: On success, the LoginForm dispatches the setCredentials Redux action, which stores the user object and token in Redux state and sets isAuthenticated to true.

Step 5: The user object and token are also saved to localStorage (so auth state survives a page refresh) and written as browser cookies (so the server-side middleware can read them on the next request).

Step 6: The user is redirected using router.replace() based on their role. Teachers go to /teacher, principals go to /principal.

Step 7: On any page refresh, the DashboardLayout dispatches the rehydrate action on mount. This reads the user and token from localStorage and restores them into Redux state, so the app does not require a re-login.

Step 8: Logout dispatches the logout action, which clears Redux state, removes the items from localStorage, and deletes the auth cookies. The user is then redirected to /login.

The Axios instance in services/api.js includes a request interceptor that automatically attaches the JWT as a Bearer token header on every outgoing request. A response interceptor catches 401 responses globally and triggers an automatic logout and redirect to /login.


3. ROLE-BASED ROUTING
----------------------

Route protection is implemented in two layers: server-side middleware and a client-side layout guard.

Server-side (proxy.js):
    This middleware runs on every request before the page loads. It reads the token cookie — if absent, the request is redirected to /login regardless of the path. It also reads the user cookie and parses the role. Requests to /teacher/* that come from a non-teacher role are redirected to the appropriate dashboard for that role. Requests to /principal/* from a non-principal role are similarly redirected. The paths /login and /live/* are treated as public and are always allowed through without any cookie check.

Client-side (DashboardLayout):
    On mount, the layout dispatches the rehydrate action to restore auth state from localStorage. If no token is found after rehydration, the layout redirects to /login. This handles edge cases where the cookie is present (so the middleware allowed the request through) but Redux state was lost — for example after a forced state reset.

Role-specific navigation is rendered based on user.role from Redux state. Teachers see links for Dashboard, Upload Content, and My Content. Principals see links for Dashboard, Approvals, and All Content. Non-matching links are never rendered, though they are also blocked by the server-side middleware.


4. API INTEGRATION APPROACH
----------------------------

All API communication is routed through the service layer. Components and hooks never import Axios or call any HTTP method directly.

The service layer pattern works as follows. Each service function is written to match the exact shape of a real API call. The mock implementation sits in place of the real one, returning the same data shape a real backend would return. To connect a real backend, only the internal return statement changes. The function signature, the hook that calls it, the Redux thunk or action that processes the result, and the component that reads from Redux — none of those change.

Example:

    Current (mock):
    export const getMyContent = async (teacherId) => {
      await delay(600)
      return contentStore.filter(c => c.teacherId === teacherId)
    }

    With real backend (one line change):
    export const getMyContent = async (teacherId) => {
      return (await api.get(`/content?teacherId=${teacherId}`)).data
    }

services/api.js contains an Axios instance configured with:
    - Base URL read from the NEXT_PUBLIC_API_URL environment variable
    - Request interceptor that reads the token from localStorage and attaches it as a Bearer authorization header
    - Response interceptor that catches 401 responses, clears auth state, and redirects the user to /login


5. STATE MANAGEMENT APPROACH
------------------------------

Redux Toolkit is used with three slices, each owning one domain of state.

authSlice stores user, token, and isAuthenticated. The setCredentials action sets all three on login. The logout action clears them. The rehydrate action reads from localStorage and restores them on page load. Auth state is the source of truth for all role checks in the UI.

contentSlice stores items (the teacher's content list), loading, error, and uploadStatus. It is used by the teacher dashboard and the my-content page through the useContent hook.

approvalSlice stores allContent (system-wide content list), loading, error, filterStatus, and searchQuery. The updateContentStatus action applies optimistic UI updates when a principal approves or rejects an item — the status is updated in Redux state immediately, without waiting for a refetch.

Custom hooks (useContent, useApprovals) encapsulate the dispatch and selector calls. A component that needs content data calls a hook function rather than importing useDispatch and useSelector directly. This keeps component files free of Redux boilerplate and makes future changes to the state shape easier to manage in one place.

Prop drilling is avoided by reading from the Redux store at the page level and passing only the minimum necessary props down to leaf components.


6. PERFORMANCE CONSIDERATIONS
-------------------------------

ContentCard and ApprovalCard are wrapped in React.memo. This prevents re-renders when the parent component re-renders but the card's own props have not changed, which is common when other parts of the approval list update.

Filtering in useApprovals is done using derived state computed inside the hook from the raw allContent array, rather than storing a separate filtered array in Redux. This avoids redundant state and ensures filters always reflect the latest data.

Images use an onError handler to fall back to a placeholder when the image URL is broken or unavailable. This prevents broken image icons in the UI.

Skeleton loaders are displayed during data fetching rather than showing nothing. This prevents layout shift and gives the user a visual indication that content is loading.

Redux selectors read minimal slices of state to limit the number of components that re-render when unrelated state changes.


7. FORM HANDLING AND VALIDATION
---------------------------------

React Hook Form is used for the login form and the upload content form. It manages form state using uncontrolled inputs internally, which means the component does not re-render on every keystroke. This keeps form interactions fast regardless of form complexity.

Zod schemas in utils/validators.js define the validation rules:

    loginSchema: validates that email is a properly formatted email address and that both fields are non-empty.

    uploadContentSchema: validates that title and subject are non-empty strings, that a file has been selected, that the file type is one of JPG, PNG, or GIF, that the file size is under 10MB, and that the end time is after the start time. The time comparison is a cross-field validation written using Zod's .refine() method.

File validation (type and size) is handled separately from Zod in the file input's onChange handler, because File objects require custom logic that Zod's standard types do not handle directly. Inline error messages are shown below each field when validation fails.


8. SCHEDULING LOGIC
--------------------

Content scheduling state is derived on the frontend from the startTime and endTime fields stored on each content item. The getSchedulingStatus function in utils/helpers.js compares these values against Date.now() at render time:

    If the current time is before startTime, the status is Scheduled.
    If the current time falls between startTime and endTime (inclusive), the status is Active.
    If the current time is after endTime, the status is Expired.

This logic is display-only. There are no cron jobs, server-side timers, or background processes involved. The status a user sees reflects the current moment at render time and does not update automatically unless the page re-renders. The public live page uses this same logic to filter which approved content to show — only items where status resolves to Active are displayed.


9. ASSUMPTIONS MADE
---------------------

Authentication is simulated with mock data. In production, the backend would validate credentials and return a signed JWT. The token string used in the mock is a placeholder and is not cryptographically signed.

File uploads store a base64 data URL in mock state. In production, the file would be sent to object storage (such as S3 or Cloudinary) and only the resulting URL would be stored and returned.

The content.service.js and approval.service.js files each maintain their own in-memory copy of mock content data within a browser session. In production, both services would read from and write to the same database via API, so updates made by the principal would be immediately visible to the teacher without any sync logic.

Teacher IDs are derived from the logged-in user's ID as stored in Redux state. No separate teacher profile lookup is performed.

The public live page at /live/:teacherId filters content by the URL parameter, returning only approved items where the current time falls within the startTime and endTime window.

No refresh token logic is implemented. The auth cookie is set with a max-age of 24 hours. After expiry, the middleware will redirect the user to /login on their next request.
